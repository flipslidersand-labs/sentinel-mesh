# ADR-005: agent↔collector 認証は per-agent トークン + ローテーションを採用し、mTLS は見送る

- 日付: 2026-09-14
- ステータス: 承認済み
- 関連 Issue: #183（per-agentトークン/ローテーション移行検討）, #184（mTLS導入検討）

## 背景

2026-09-13 の全体レビューで、現在の認証方式（gRPC/REST 双方とも単一の
`SENTINEL_API_TOKEN` 共有シークレットのみ）に構造的な弱点があると指摘された。

- ローテーション機構が無く、トークン変更は全 agent/全 UI クライアントへの再配布が必要
- per-agent 識別が無く、1 台の資格情報漏洩が全 agent のなりすましを許す

これに対し #183（per-agentトークン発行への移行）と #184（agent↔collector
間の mTLS 導入）の 2 つの対策候補が別々に起票されたが、両者は同じ問題
（「正しい agent が接続していることをどう証明するか」）に対する代替案であり、
どちらか一方（または両方）を選んでから着手すべきだったため、本 ADR で
まとめて方針を決定する。

## 検討した選択肢

### A. per-agent Bearer トークン + ローテーション（#183 が提案）

node_id 単位でトークンを発行・検証する。既存の Bearer 認証の delivery
機構（`Authorization: Bearer <token>`）をそのまま使い、collector 側で
「どのトークンがどの node_id に対応するか」を保持する点のみが変わる。

- 実装コスト: 小〜中。既存の `httpauth`/gRPC interceptor の比較ロジックを
  「1 つの定数と比較」から「トークンストアに存在するか + 対応する node_id
  を取得」に変える程度。トークンストア自体は BadgerDB に素直に乗る。
- 運用コスト: 小。トークンの発行・失効は `token add/revoke <node_id>` 的な
  CLI 一発で完結し、PKI・CA・証明書更新スケジュールの運用が要らない。
- 失効(revocation)の確実性: 高い。ストアから該当トークンを削除すれば
  即座に失効する（CRL/OCSP のような伝播遅延が無い）。

### B. mTLS（agent 側クライアント証明書、#184 が提案）

TLS の相互認証で agent の身元を証明する。

- 実装コスト: 中〜大。CA の構築・証明書発行フロー・agent 配布時の証明書
  同梱・collector 側の証明書検証ロジックが新規に必要。
- 運用コスト: 大。証明書の有効期限管理、更新（renewal）、失効
  （CRL または OCSP スタックの運用）が継続的に発生する。本プロジェクトは
  個人運用の自宅ラボ規模（現状 agent 数は数台〜十数台程度）であり、
  専任の PKI 運用体制を前提にできない。
- 失効の確実性: 理論上は A と同等以上だが、CRL/OCSP を運用しない簡易構成
  （証明書の有効期限のみに依存）にすると、漏洩から証明書失効までの
  ウィンドウが空きやすい。

### C. 現状維持（トークンローテーション手順のドキュメント化のみ）

実装コストはゼロだが、per-agent 識別ができない構造的弱点は残る。
#183/#184 が指摘した「1 台漏洩で全 agent なりすまし」のリスクを
運用ドキュメントだけで緩和するのは不十分と判断し、採用しない。

## 決定

**A（per-agent Bearer トークン + ローテーション）を採用する。mTLS（B）は
見送る。** UI↔collector は現状どおり単一トークンでの Bearer 認証を継続する
（ブラウザクライアントに証明書を配布する運用は非現実的なため、mTLS の
対象は最初から agent↔collector チャネルのみだった — UI 側の認証強化は
本 ADR のスコープ外）。

実装は #183 側で進める。#184 はこの決定により対応不要と判断し、本 ADR を
理由としてクローズする。

## 理由

- 本プロジェクトの規模（個人運用・agent 数十数台程度）では、mTLS が要求する
  CA/証明書ライフサイクル運用のコストが、得られるセキュリティ向上に見合わない。
- per-agent トークンでも「1 台漏洩で全体なりすまし」というレビュー指摘の
  核心的なリスクは解消でき、かつ失効がトークンストアからの削除一発で
  完結し運用がシンプル。
- 既存の Bearer 認証機構（httpauth・gRPC interceptor）を流用できるため、
  実装差分が小さく回帰リスクが低い。

## トレードオフ

- 盗聴・改ざん耐性は引き続き輸送層の TLS（サーバ証明書検証のみ）に依存する。
  mTLS が提供する「クライアントの真正性を暗号的に輸送層で証明する」層は
  持たない — アプリケーション層（Bearer トークン検証）でのみ真正性を保証する。
- agent 台数が将来大きく増え、専任の PKI 運用体制を持てる規模になった場合は
  mTLS を再検討する余地がある。その場合は本 ADR を新しい ADR で上書きする。

## 移行手順（#193 の決定）

既存の単一共有 `SENTINEL_API_TOKEN` から per-agent トークンへの移行は、
**無停止移行の仕組みを実装しない**。理由:

- 本プロジェクトの規模（個人運用・agent数十数台程度）では、全 agent を
  ほぼ同時に再デプロイしてダウンタイムを許容する一括切替で十分実用的。
- 無停止移行（新旧トークンの二重受理期間を設ける等）は、`checkAuth`
  にレガシーフォールバック分岐を追加し、その分岐をいつ・誰が削除するかの
  運用ルールまで必要になる — 本 ADR の全体方針（このスケールでは運用コストが
  嵩む仕組みを避ける）と矛盾する。
- 移行手順: 新しい collector バイナリ（per-agent トークン対応版、#189/#190）
  をデプロイ → 各 agent に `token issue <node_id>` で発行したトークンを
  `scripts/deploy-agent.sh`（#192）で配布・再起動、の順で1台ずつ切り替える。
  切替中の対象 agent は一時的にイベント送信が止まるが、他 agent には影響しない。

## 影響を受ける Issue

- #183: 本 ADR の決定に従い実装を進める（このまま進行）。
- #184: 本 ADR によりクローズ（mTLS 見送りの決定が結論）。
- #193: 本 ADR の「移行手順」決定によりクローズ（無停止移行は見送り）。
